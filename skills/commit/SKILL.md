# Git Commit 智能生成

自动分析 git diff，生成符合规范的 commit 信息，支持拆分多个 commit。默认自动 stage 全部改动（可用 `--staged` 关闭）。

## 工作流程

### 1. 获取改动（支持 `--staged` 参数）

**默认行为：暂存区为空时自动 `git add .`，尊重用户已暂存内容。**

判定逻辑：

- **传入 `--staged`**：严格只读当前暂存区，不自动 add
  - `git diff --cached` 为空 → 提示"没有暂存的改动，请先 git add 需要提交的文件"，结束流程
  - 有内容 → 继续分析
- **未传 `--staged`（默认）**：
  - `git diff --cached` 有内容 → 直接分析已暂存内容（**不再**额外 `git add`，避免覆盖用户已做选择）
  - `git diff --cached` 为空 → 检查工作区是否有未暂存改动（modified / deleted / untracked）
    - 无改动 → 提示"没有可提交的改动"，结束流程
    - 有改动 → 执行 `git add .` 自动 stage，然后继续分析

**原则：** 主动触发 commit 通常是想交当前所有改动，故默认自动 stage；`--staged` 保留旧行为，供「只提交已手动暂存部分」的场景使用。

### 2. 分析并分组

分析 diff 内容，判断：
- **改动类型**（新功能 / bug 修复 / 重构 / 文档 / 测试 / 杂项）
- **是否拆分**：多个不相关改动应拆分为多个 commit

**拆分原则：**
1. 按功能分组 - 相关文件归为同一 commit
2. 按类型分组 - feat/fix/docs/test 分开
3. 按模块分组 - 不同模块的改动分开

### 3. 生成 commit 信息

**格式：**
```
<type>: <描述>
```

**类型映射：**
| 类型 | 用途 | 判断依据 |
|------|------|----------|
| feat | 新功能 | 新增文件、新 API、新组件、新业务逻辑 |
| fix | 修复 bug | 错误处理、边界条件、修复已知问题 |
| refactor | 重构 | 代码重组、优化结构、不改变功能 |
| docs | 文档 | README、注释、文档文件 |
| test | 测试 | 测试文件、测试用例 |
| chore | 杂项 | 配置、依赖、构建脚本 |

**描述要求：**
- 中文，简洁直白
- 不超过 50 字符
- 动词开头（添加、修复、优化、更新、删除）
- 不加句号

**示例：**
```
feat: 添加用户导出功能
fix: 修复登录超时问题
refactor: 简化支付流程
docs: 更新 API 文档
test: 添加订单模块测试
chore: 更新依赖版本
```

### 4. 风险判定与确认

**默认行为：直接提交，不询问。**

先打印建议的 commit message + 涉及文件（保持透明，给用户一眼喊停的窗口）。
未命中下列任一风险场景 → 直接进入第 5 步执行提交，**不弹询问**。

**风险场景判定（命中任一即弹询问）：**

| 风险场景 | 判定条件 |
|---------|---------|
| 多 commit 拆分 | 分析阶段判断需拆分为 >1 个 commit |
| 删除文件 | 暂存 diff 含文件删除（`deleted:` / 文件状态为 `D`） |
| 配置/依赖变更 | 命中 `package.json`、`pnpm-lock.yaml`/`package-lock.json`/`yarn.lock`、`settings.json`、`.env*`、CI 配置（`.github/workflows/*`、`.gitlab-ci.yml` 等）、构建配置（`vite.config.*`/`webpack.config.*`/`tsconfig.json` 等） |
| 大批量改动 | 单个 commit 涉及文件数 ≥ 10 |

**询问方式：一律用 `AskUserQuestion` 工具弹选项点选，禁止要求用户手打 y/n/edit。**

**单 commit 命中内容风险时**（删除文件 / 配置依赖变更 / 大批量改动），弹一次：
- question：`检测到【删除文件】，建议提交「feat: 添加用户导出功能」，是否继续？`（把【】内换成实际命中的风险，多个风险并列写出）
- header：`提交确认`
- options：
  1. `确认提交` — 使用建议的 message 直接提交
  2. `修改 message` — 让用户给出新的 commit message 后提交
  3. `取消提交` — 不提交

**多 commit 拆分场景：只确认一次「拆分方案是否合理」，不逐个问子 commit。**
- question：列出完整拆分方案（每个子 commit 的 message + 文件清单），并在文案中标注命中的内容风险，例如：`建议拆分为 3 个 commit（其中 [2/3] 含删除文件、[3/3] 含依赖变更），拆分方案是否合理？`
- header：`拆分方案确认`
- options：
  1. `方案合理，全部提交` — 按方案逐个执行所有 commit，不再逐个询问
  2. `方案需调整` — 让用户说明哪里不合理（哪几个该合并 / 该再拆 / 某 message 不对），据此重新生成或调整后再确认
  3. `取消` — 放弃本次提交

### 5. 执行提交

```bash
git commit -m "<commit信息>"
```

## 边界处理

- **非 git 仓库**：提示"当前不是 git 仓库"
- **无可提交改动**：默认模式下工作区与暂存区均为空时提示"没有可提交的改动"；`--staged` 模式下暂存区为空时提示"没有暂存的改动，请先 git add 需要提交的文件"

## 约束

- **stage 规则：** 默认行为在暂存区为空时自动 `git add .`；暂存区非空时直接使用已暂存内容；传入 `--staged` 时只读当前暂存区，不自动 add
- 不添加 scope、breaking change 标记、co-author、issue 关联
- 保持简洁，避免冗余
- 默认直接提交；仅在「多 commit 拆分 / 删除文件 / 配置依赖变更 / 大批量改动（≥10 文件）」场景才询问
- 多 commit 拆分场景**只确认一次拆分方案是否合理**，确认后所有子 commit 一并执行，**不逐个子 commit 询问**
- 一律通过 `AskUserQuestion` 选项点选确认，**不得**要求用户手打 `y/n/edit/skip`
