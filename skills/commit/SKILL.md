# Git Commit

## 1. 确定提交范围

- 先确认当前目录是 Git 仓库并读取状态。
- 带 `--staged`：只分析 `git diff --cached`；为空则提示先暂存并停止。
- 默认：暂存区非空时只处理现有暂存内容；暂存区为空且工作区有改动时执行 `git add .`；完全无改动则停止。

不要把用户已选择的暂存集合与其他工作区改动混在一起。

## 2. 分析与拆分

按业务目的优先分组，再参考类型和模块。多个不相关功能、修复、文档或测试应拆分；同一行为的实现、测试和文档可保持原子提交。

提交信息格式为 `<type>: <中文描述>`：

- `feat` 新功能，`fix` 修复，`refactor` 重构，`docs` 文档，`test` 测试，`chore` 配置/依赖/构建。
- 描述以动词开头，不超过 50 个字符，不加句号。
- 不添加 scope、breaking change、co-author 或 issue 标记。

## 3. 风险确认

先展示建议 message 和文件。默认直接提交；仅命中以下任一情况时确认：

| 风险 | 条件 |
|---|---|
| 多 commit | 需要拆成 2 个及以上提交 |
| 删除 | 暂存状态含 `D` |
| 配置/依赖 | 依赖与锁文件、`.env*`、CI、构建或主要工具配置 |
| 大批量 | 单个 commit 至少 10 个文件 |

优先使用宿主的结构化选择工具：

- 单 commit：`确认提交 / 修改 message / 取消提交`，问题中列出命中的风险。
- 多 commit：一次展示完整拆分方案、各 message、文件及风险，提供 `方案合理，全部提交 / 方案需调整 / 取消`；确认后不逐个再问。
- 宿主没有结构化选择工具时，使用同样的三个编号选项，不要求用户输入 `y/n/edit`。

## 4. 提交

按已展示且获确认的范围执行 `git commit -m "<message>"`。多 commit 使用精确路径控制每组暂存内容；任一步失败就停止，报告真实 Git 状态，不继续后续提交。
