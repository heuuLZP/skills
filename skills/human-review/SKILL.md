# 人工审阅

默认使用用户语言。若并非显式调用，立即退出本工作流，不暂存、修改或提交代码。

## 不可破坏的边界

- 未获当前批次明确授权，不编辑或提交；授权只覆盖已展示的当前批次路径和方案。
- 禁止 `git add .`、`git add -A`、`git commit -a`、`git reset --hard`、`git checkout --`、`git restore <path>` 及破坏性等价命令。
- 仅用精确路径改变索引；不得丢弃工作区内容，也不得取消 skill 启动前已有的暂存。
- 默认每批 1–2 个文件；仅强耦合的实现、类型或测试可合为最多 3 个。
- 批准只对刚展示的暂存差异有效。修复、Git hook 或外部编辑改变差异后必须重新审阅、重新批准。
- 批次外文件需要单独授权；不得启动子代理，除非用户明确要求。

## 1. 建立基线与批次

1. 读取 `git status --short`、已暂存/未暂存 diff、未跟踪、重命名、删除和冲突；无改动则停止。
2. 记录启动前暂存的路径和内容。已有暂存优先作为首批；若超过 3 个文件或职责混杂，说明冲突并询问如何处理，不自行重组。
3. 按业务目的、依赖和行为职责分批，不按文件名机械分组。分开无关功能、修复、文档、生成文件和配置，标记删除、依赖、锁文件、CI、迁移等风险。
4. 文件同时含目标与无关片段时，先取得按片段暂存授权。

首次只展示整体目标、文件数/批次数、职责分组、风险分布和当前批；后续仅更新进度与剩余风险。

## 2. 暂存并验证当前批

使用 `git add -- <path>...` 等精确路径命令。随后检查 `git diff --cached --name-status` 和 `git diff --cached`，确认索引没有混入其他新路径。错误时只修复索引，不触碰工作区内容。

## 3. 展示当前批

始终根据暂存 diff，按以下顺序简洁展示：

1. 批次职责和目标。
2. 问题发现：`阻断 / 关注 / 建议`，包含编号、`path:line`、依据；可安全修复时补充拟改路径、预期行为和验证方式。
3. 每个文件的职责、1–2 个关键改动、原因、行为影响；高风险逻辑最多 4 点，并说明失败模式与兼容性。无依据的原因标为推断。
4. 必要时说明跨文件调用链、数据流或依赖。
5. 工程质量矩阵：正确性、职责边界、可读性、可维护性、实现简洁性，使用 `🟢 通过 / 🟡 关注 / 🔴 问题`。通过项不写套话，其他项引用已有问题编号。
6. 实际执行过的验证，以及建议提交信息。

问题分类：

- `阻断`：已确认缺陷、安全/数据风险、本次改动导致的验证失败、冲突或展示与暂存差异不一致。
- `关注`：有明确风险或不确定性，但尚无证据证明必然错误。
- `建议`：不影响提交的质量优化。

不要因测试数量或覆盖率创建问题。提交信息使用小写 Conventional Commit 类型，中文动词开头、50 字内、不加句号，不添加 scope、breaking change、co-author 或 issue 标记。

## 4. 获取决定

优先使用结构化选择，正文保留详细分析，选择只保留短文案：

- 无阻断：`提交本批 / 修改本批 / 暂停审阅`。
- 有阻断：不得提供提交入口；使用 `修复本批 / 跳过本批 / 暂停审阅`。

暂停或跳过时只撤销本 skill 为当前批新增的暂存，保留工作区和原有暂存。宿主无结构化选择时列相同的三个编号选项。模糊回复、沉默或前一批批准都不构成授权。

## 5. 执行授权修改

修改前重新记录状态和暂存边界，只编辑已展示且获授权的路径。运行直接相关且不会重写无关文件的验证，重新检查完整 diff、精确暂存并完整展示本批，要求新的提交批准。

若必须扩展到批次外文件，先说明路径、必要性和职责关系，再询问 `允许扩展 / 调整方案 / 暂停审阅`。扩展后超过 3 个文件或混入独立职责时重新分批。

修复或验证失败、差异被外部改变、出现新阻断或无法隔离片段时停止提交并保留全部工作。

## 6. 提交与循环

提交前确认暂存路径和内容仍与展示一致，再用已批准的 message 提交。报告哈希和标题，重新读取 Git 状态后进入下一批。全部完成时汇总创建的提交及仍未暂存、已暂存、未跟踪、跳过或冲突的内容。

遇到未解决冲突、无法确定安全批次、提交失败或用户暂停时停止，说明当前索引/工作区状态和恢复所需下一步。
