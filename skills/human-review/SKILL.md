# 人工审阅（批次模式）

默认使用用户语言。若并非显式调用，立即退出本工作流，不修改任何内容。

显式调用即授权对**未 push 的本地提交批次**完成审阅闭环：验证、审阅累计 diff、修复可确定问题并追加修复提交。仅在需要用户做核心决策时暂停。

**执行方式**：在主会话中调用时，优先 spawn `fresh-reviewer` 子代理执行本技能（全新上下文，避免同会话自我审查污染）。当前执行者已是 fresh-reviewer、用户要求就地快速审阅、或子代理不可用（非 ZCode 环境）时，就地执行。

## 不可破坏的边界

- **完全无视工作区**：不暂存、不提交、不修改工作区任何内容（含未跟踪文件），也不要求工作区干净。多会话并行时工作区可能存在其他会话的进行中改动，一律不碰、不列为遗留。
- 只处理提交：所有操作针对 `origin/<当前分支>..HEAD` 的提交与累计 diff；无未 push 提交则报告并停止。
- 修复以**追加提交**落地（精确路径暂存修复文件）；不改写已有提交历史（不 rebase、不 amend、不 reset）。
- 禁止 `git add .`、`git add -A`、`git commit -a`、`git reset --hard`、`git checkout --`、`git restore <path>` 及破坏性等价命令。
- 验证执行（测试/lint/typecheck 及基线对照）与探索简报可委派 light-runner 子代理并行完成；审阅判断、修复决策与提交决策不得委派。
- 不 push。

## 1. 建立批次基线（双轨启动）

1. **双轨启动**：第一步即把验证执行（typecheck/lint/定向 lint/相关测试）与探索简报（`origin/分支..HEAD` 提交清单与累计 diff 统计、改动文件按模块分组、涉及的导出符号与跨文件契约点、AGENTS.md 相关约定）委派 light-runner 后台并行；等待期间同步读取提交清单与累计 diff，简报到手后不重复这些探索。
2. 确定批次：`git log origin/<分支>..HEAD --oneline` 与 `git diff origin/<分支>...HEAD --stat`；ahead 为 0 → 报告"无未 push 提交"并停止。

## 2. 自动审阅

1. 审阅累计 diff：正确性、职责边界、可读性、可维护性、实现简洁性，以及**跨提交视角**——前一提交引入、后一提交又改动或抵消的问题，攒批审阅时必须显式检查。
2. 阅读分层：默认只读 diff 及其上下文，仅对公共层、跨模块契约相关文件和新增文件做全文精读；验证结论直接采用 light-runner 的判定（通过/新增失败/存量失败/无法判定），不重复执行，仅当判定为"无法判定"或与改动强相关时才定向补跑单项。
3. 发现可确定且可安全修复的问题：直接修复、增量复审（只复查 delta + 定向 lint，不重跑全量）、以修复提交追加。不为修复请求授权。
4. 修复提交信息优先遵循仓库约定；若无约定，使用小写 Conventional Commit 类型，中文动词开头、50 字内、不加句号，不添加 scope、breaking change、co-author 或 issue 标记。

## 3. 决策边界

只在以下核心决策上暂停（或经 fresh-reviewer 上报），并提供已验证事实、建议选项和取舍：

- 产品行为、兼容性、数据语义、公共接口或架构存在多个合理选择，无法从仓库证据唯一确定。
- 修复需要引入新功能、越出本批次提交的自然范围，或会覆盖他人工作。
- 操作具有不可逆或高影响后果。

## 4. 问题分级

- `阻断`：已确认缺陷、安全或数据风险、本批提交导致的验证失败。可自动修复则修复；需核心决策则上报。
- `关注`：有明确风险或不确定性。能通过代码、文档或验证消除时自动调查；剩余不确定性构成核心决策时上报。
- `建议`：不影响正确性的质量优化。默认不追加改动。

## 5. 完成汇总

- 批次概况：审阅的提交数、累计 diff 规模、跨提交发现。
- 追加的修复提交：哈希、标题、修复内容与行为影响。
- 验证结果：light-runner 判定汇总（通过/新增失败/存量失败/无法判定）。
- 遗留决策与建议（如无写"无"）；明确说明工作区未做任何改动。
