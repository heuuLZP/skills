# 人工审阅

默认使用用户语言。若并非显式调用，立即退出本工作流，不暂存、修改或提交代码。

显式调用即授权在当前待处理改动范围内完成闭环：按精确路径暂存、审阅、执行直接相关验证、修复可确定问题并提交。不要对每个批次、修复或提交重复请求确认。

## 不可破坏的边界

- 禁止 `git add .`、`git add -A`、`git commit -a`、`git reset --hard`、`git checkout --`、`git restore <path>` 及破坏性等价命令。
- 仅用精确路径改变索引；不得丢弃工作区内容，也不得取消技能启动前已有的暂存。
- 不得把“修复当前改动”扩大成无关重构、新功能或独立职责。
- 验证执行（测试/lint/typecheck 及基线对照）与探索简报可委派 light-runner 子代理并行完成；审阅判断、修复决策与提交决策不得委派。
- 修复、格式化、Git hook 或外部编辑改变差异后，必须重新审阅实际差异，但无需因此再向用户请求批准；复审只针对自上次审阅以来的 delta 及其受影响区域，验证用增量方式（增量 typecheck、按文件 lint、相关测试 --related），不重跑全量。
- 提交前确认暂存路径、差异和提交职责一致；始终保留批次外的工作区内容。

## 1. 建立基线与提交地图

1. **双轨启动**：第一步即把验证执行（typecheck/lint/定向 lint/相关测试）与探索简报（diff 统计、改动文件按模块分组、涉及的导出符号与跨文件契约点、AGENTS.md 相关约定）委派给 light-runner 后台并行；在其返回前同步推进下列基线工作，简报到手后不再重复这些探索。
2. 读取 `git status --short`、已暂存与未暂存 diff、未跟踪、重命名、删除和冲突；无改动则停止。
3. 记录启动前已暂存的路径和内容。已有暂存优先处理，不得静默拆分或取消。
4. 按单一提交职责、依赖和行为目标分批，不按文件数量机械拆分。同一职责的实现、类型、测试、文档或锁文件可同批；无关功能、修复、配置和生成产物应分开。
5. 以尽量少的连贯批次完成工作。首次只简要报告整体目标、职责分组和主要风险，不等待用户确认即继续。

如果启动前暂存已混合多个独立职责，且无法在不改变用户原有索引意图的情况下安全处理，这属于需要用户决策的边界。

## 2. 自动审阅循环

对每个批次连续执行，不在步骤间等待确认：

1. 使用 `git add -- <path>...` 等精确路径命令暂存，然后检查 `git diff --cached --name-status` 和 `git diff --cached`，确认没有混入其他路径或片段。
2. 根据实际暂存 diff 评估正确性、职责边界、可读性、可维护性和实现简洁性。阅读分层：默认只读 diff 及其上下文，仅对公共层、跨模块契约相关文件和新增文件做全文精读；验证结论直接采用 light-runner 的判定（通过/新增失败/存量失败/无法判定），不重复执行，仅当判定为"无法判定"或与改动强相关时才定向补跑单项。
3. 发现可确定且可安全修复的问题时，直接修复、重新验证、重新检查完整 diff 并精确暂存。不为这个循环请求授权。
4. 当批次达到“全绿”时直接提交：无未解决的确认缺陷或核心决策，已执行的相关验证通过，暂存差异与单一职责一致。
5. 提交后报告短哈希、标题、关键改动和验证结果，重新读取 Git 状态并继续下一批。

只有“全绿”批次可自动提交。不得因测试数量、覆盖率或与本次改动无关的现有失败创建问题；只如实记录其对当前结论的影响。

## 3. 自动修复与决策边界

满足以下条件时直接修复：预期行为可从现有代码、规范、测试或改动目标唯一确定；修复是局部、可逆且不引入新产品行为；所需路径属于当前职责及其直接实现、类型或测试。

只在以下核心决策上暂停，并提供已验证事实、建议选项和取舍：

- 产品行为、兼容性、数据语义、公共接口或架构存在多个合理选择，无法从仓库证据唯一确定。
- 修复需要引入新功能、处理独立职责、越出当前待处理改动的自然范围，或会覆盖用户同一区域的工作。
- 操作具有不可逆或高影响后果，包括数据迁移、安全策略、生产配置、对外发布或需要额外凭据与外部环境。
- 启动前已暂存内容需要拆分或重组，或无法安全隔离目标片段。

仅当需要用户选择时才停下等待回复。工具、验证或提交失败时，先自动诊断并尝试安全解决；只有反复失败、环境不可用或需要新权限时才停止，说明当前索引、工作区状态和继续所需条件。

## 4. 问题与提交标准

- `阻断`：已确认缺陷、安全或数据风险、本次改动导致的验证失败、冲突，或展示与暂存差异不一致。可自动修复则修复；需要核心决策则暂停。
- `关注`：有明确风险或不确定性。能通过代码、文档或验证消除时自动调查；仅在剩余不确定性构成核心决策时暂停。
- `建议`：不影响正确性或当前目标的质量优化。默认不扩大改动，也不阻止全绿提交。

提交信息优先遵循仓库约定；若无约定，使用小写 Conventional Commit 类型，中文动词开头、50 字内、不加句号，不添加 scope、breaking change、co-author 或 issue 标记。

## 5. 完成汇总

全部处理后统一汇总：

- 已创建的提交哈希、标题、职责和验证。
- 自动修复的问题及对行为的影响。
- 仍未暂存、已暂存、未跟踪、冲突或未处理的内容。
- 若曾暂停，需要用户决定的唯一问题和建议选项。
